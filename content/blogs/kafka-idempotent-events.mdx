## The Challenge

RDT (Radio Data Terminal) scanners in Maersk warehouses emit container scan events over intermittent WiFi. When a terminal loses connectivity and reconnects, it replays buffered events — sometimes delivering the same scan event 2–5 times.

At global scale (50+ countries, hundreds of terminals), duplicate events aren't rare edge cases. They're a daily operational reality.

## Kafka Delivery Semantics

Kafka guarantees **at-least-once** delivery by default. Your consumer will process a message at least once, but may process it more than once if:
1. The consumer crashes before committing its offset
2. A rebalance occurs mid-processing
3. The producer retries (our terminal firmware does this)

To achieve **exactly-once semantics** at the application layer, you need idempotent consumers.

## The Lock Lease Pattern

We use DynamoDB as a distributed lock store. Each scan event carries a `correlation_id` generated by the terminal:

```go
type ScanEvent struct {
    CorrelationID string    `json:"correlation_id"` // terminal-generated UUID
    ContainerID   string    `json:"container_id"`
    ScanTime      time.Time `json:"scan_time"`
    TerminalID    string    `json:"terminal_id"`
}
```

Before processing, we attempt to claim the lock:

```go
func (s *ScanService) ProcessEvent(ctx context.Context, event ScanEvent) error {
    claimed, err := s.lockStore.Claim(ctx, event.CorrelationID, 30*time.Second)
    if err != nil {
        return fmt.Errorf("lock claim: %w", err)
    }
    if !claimed {
        // Duplicate — already processed or being processed
        return nil
    }
    defer s.lockStore.Release(ctx, event.CorrelationID)

    return s.processInternal(ctx, event)
}
```

The DynamoDB conditional write:

```go
func (l *DynamoLockStore) Claim(ctx context.Context, id string, ttl time.Duration) (bool, error) {
    expiry := strconv.FormatInt(time.Now().Add(ttl).Unix(), 10)
    _, err := l.client.PutItem(ctx, &dynamodb.PutItemInput{
        TableName: aws.String(l.table),
        Item: map[string]types.AttributeValue{
            "pk":     &types.AttributeValueMemberS{Value: id},
            "expiry": &types.AttributeValueMemberN{Value: expiry},
        },
        ConditionExpression: aws.String("attribute_not_exists(pk)"),
    })
    if err != nil {
        var ccfe *types.ConditionalCheckFailedException
        if errors.As(err, &ccfe) {
            return false, nil // already exists — duplicate
        }
        return false, err
    }
    return true, nil
}
```

DynamoDB's TTL feature automatically cleans up expired locks — no maintenance job needed.

## Handling Out-of-Order Events

Kafka partitioning by `terminal_id` guarantees ordering within a terminal, but cross-partition ordering is not guaranteed. Our downstream service builds a container movement timeline, so we need to handle out-of-order delivery.

Solution: store events with their `scan_time` and build the timeline on read, not on write. The consumer writes each event to DynamoDB keyed by `(container_id, scan_time)`. Queries reconstruct the timeline sorted by `scan_time`.

```go
// Write: order doesn't matter
pk := fmt.Sprintf("CONTAINER#%s", event.ContainerID)
sk := fmt.Sprintf("SCAN#%s", event.ScanTime.UTC().Format(time.RFC3339Nano))

// Read: query sorted by SK = chronological order
```

## Testing Idempotency

Write a table-driven test that simulates duplicates:

```go
func TestProcessEvent_Idempotent(t *testing.T) {
    store := newInMemoryLockStore()
    svc := NewScanService(store, newInMemoryScanRepo())
    
    event := ScanEvent{
        CorrelationID: "test-uuid-123",
        ContainerID:   "MRKU1234567",
        ScanTime:      time.Now(),
    }
    
    // First call: should process
    err := svc.ProcessEvent(context.Background(), event)
    require.NoError(t, err)
    
    // Second call (duplicate): should no-op
    err = svc.ProcessEvent(context.Background(), event)
    require.NoError(t, err)
    
    // Only one scan record should exist
    scans, _ := svc.GetScans(context.Background(), event.ContainerID)
    assert.Len(t, scans, 1)
}
```

## Operational Results

- **Duplicate rate**: ~0.3% of daily events (driven by terminal firmware retries)
- **False positives** (legitimate rescans rejected): 0 (TTL ensures locks expire before legitimate re-scans)
- **DynamoDB cost**: negligible — lock items are tiny and expire automatically
