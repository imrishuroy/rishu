Press the elevator close-door button once. Nothing happens. Press it five more times. The door still closes exactly once. That button is idempotent: extra presses produce no extra effect.

This matters in software for the same reason it matters in elevators. When a network fails and a client retries, the server may receive the same request twice. If the operation is not idempotent, you get two effects from one intent. A payment runs twice. A container is logged at a location it was never at. A customer gets two confirmation emails.

This post starts from that simple idea and builds up to a complete production system that handles duplicate scan events from warehouse Radio Data Terminals. You will see the theory, the full Go implementation, the tests, and the tradeoffs. By the end you will know exactly how to design an idempotent Kafka consumer and why each decision was made.

## What Idempotent Means

In mathematics, a function f is idempotent when f(f(x)) = f(x). Applying it twice produces the same result as applying it once.

Some operations are naturally idempotent:

```sql
-- Sets a value. Run it ten times, same result.
UPDATE users SET name = 'Rishu' WHERE id = 42;

-- NOT idempotent. Each run removes another $100.
UPDATE accounts SET balance = balance - 100 WHERE id = 42;
```

The difference is whether the operation *sets* a value or *changes* it. Setting is idempotent. Incrementing is not.

HTTP methods work the same way. GET is idempotent: fetching a resource does not modify it. PUT is idempotent: replacing a resource with the same data leaves the same state. POST is not: each call to `POST /orders` creates a new order.

In distributed systems you want your event consumers to be idempotent. The infrastructure may deliver the same event multiple times, and your consumer should produce the same outcome each time it receives the same event.

## Why Distributed Systems Deliver Events More Than Once

Networks fail. Processes crash. At scale this is not a theoretical concern; it happens daily.

Here is a concrete failure sequence with a Kafka consumer:

1. Consumer reads message M from a Kafka partition
2. Consumer processes M and writes the result to a database
3. Consumer crashes before it commits the offset back to Kafka
4. Kafka does not see the commit, so it redelivers M to the next consumer instance
5. The same message is now processed twice

This is called **at-least-once delivery**. The message is guaranteed to be processed at least once, but may be processed more than once.

Kafka actually has three delivery modes:

**At-most-once**: commit the offset before processing. If the consumer crashes during processing, the message is lost and never retried. Acceptable for telemetry where losing a few data points is fine. Unacceptable for anything financial or inventory-related.

**At-least-once**: process first, then commit the offset. No messages are lost, but duplicates are possible on failure. This is the default and the most common choice.

**Exactly-once**: Kafka supports this through transactions, but only within Kafka itself. The moment your consumer writes to an external system like a database, you are back to at-least-once at the application layer. Kafka transactions do not wrap external writes.

The practical conclusion: choose at-least-once delivery and design your consumer to be idempotent at the application level. That is what we did.

## Radio Data Terminals: The Real Problem

A Radio Data Terminal (RDT) is a handheld barcode scanner used in shipping warehouses. Workers scan container barcodes as containers move through a facility. Each scan emits an event that says "container X was scanned at location Y at time T."

These terminals connect over warehouse WiFi. Warehouse WiFi is not like home WiFi. Forklifts block signals. Metal shelving racks create dead zones. A terminal that walks into a dead zone buffers its events in local flash memory and replays them when connectivity returns.

The firmware does not know whether the events it sent before the disconnect were received. So it sends everything again. Depending on how long the connection was down and how the firmware is configured, the same scan event may arrive two to five times.

At one warehouse this is a minor nuisance. At 50+ countries with hundreds of terminals each, duplicates arrive constantly. On a normal day, about 0.3% of all events are duplicates. During a major network event at a hub, that number spikes higher.

The scan events flow through Kafka. The consumer that processes them must handle this cleanly.

## Correlation IDs: Recognizing a Duplicate

To deduplicate events, you need a way to tell whether two events represent the same real-world scan. The RDT firmware generates a UUID for each scan before it sends the event. If it retries, the retry carries the same UUID.

This UUID is the **correlation ID**. Two events with the same correlation ID are the same scan, regardless of how many times the terminal sent them.

```go title="events.go"
package events

import "time"

// ScanEvent represents a single container scan from an RDT terminal.
type ScanEvent struct {
	CorrelationID string    `json:"correlation_id"` // UUID v4 generated by the terminal
	ContainerID   string    `json:"container_id"`   // e.g. MRKU1234567
	ScanTime      time.Time `json:"scan_time"`
	TerminalID    string    `json:"terminal_id"`
	LocationCode  string    `json:"location_code"` // e.g. BEANR-W1
}
```

The terminal uses UUID v4 (random). The probability of a collision between two different scans is roughly 1 in 2^122. In practice this never happens. If your firmware is poorly written and you suspect it might reuse UUIDs, you can use `(terminal_id, scan_time)` as the dedup key instead. A terminal physically cannot scan two containers at the exact same nanosecond.

The consumer's job is simple: if you have seen this correlation ID before, ignore the event. If you have not, process it and record that you have seen it.

## Three Patterns for Idempotent Consumers

### Pattern 1: Unique Database Constraint

The simplest approach. Create a table for processed events and put a unique constraint on the correlation ID. A duplicate insert fails, which you catch and ignore.

```sql title="schema.sql"
CREATE TABLE processed_scans (
    correlation_id TEXT PRIMARY KEY,
    container_id   TEXT        NOT NULL,
    scan_time      TIMESTAMPTZ NOT NULL,
    terminal_id    TEXT        NOT NULL,
    location_code  TEXT        NOT NULL,
    processed_at   TIMESTAMPTZ DEFAULT now()
);
```

```go title="postgres_handler.go"
func (s *ScanService) ProcessEvent(ctx context.Context, event events.ScanEvent) error {
	_, err := s.db.ExecContext(ctx, `
		INSERT INTO processed_scans
			(correlation_id, container_id, scan_time, terminal_id, location_code)
		VALUES ($1, $2, $3, $4, $5)
		ON CONFLICT (correlation_id) DO NOTHING
	`, event.CorrelationID, event.ContainerID, event.ScanTime,
		event.TerminalID, event.LocationCode)
	if err != nil {
		return fmt.Errorf("insert processed scan: %w", err)
	}

	// Only reaches here if the insert succeeded (not a duplicate).
	return s.updateContainerLocation(ctx, event)
}
```

`ON CONFLICT DO NOTHING` turns a duplicate constraint violation into a silent no-op. Clean and simple.

The main downside is that the `processed_scans` table grows indefinitely. You need a periodic job to delete old records, or you partition the table by date and drop old partitions. This adds operational overhead.

Use this pattern when you already have PostgreSQL in your stack and your event rate is moderate (under a few thousand per second per consumer).

### Pattern 2: Redis SETNX

Redis's `SETNX` (set-if-not-exists) is atomic and fast. Pair it with a TTL and you get automatic cleanup.

```go title="redis_handler.go"
func (s *ScanService) ProcessEvent(ctx context.Context, event events.ScanEvent) error {
	key := "dedup:" + event.CorrelationID

	// SetNX returns true if the key was newly set, false if it already existed.
	ok, err := s.redis.SetNX(ctx, key, "1", 24*time.Hour).Result()
	if err != nil {
		return fmt.Errorf("redis setnx: %w", err)
	}
	if !ok {
		return nil // duplicate, skip
	}

	return s.updateContainerLocation(ctx, event)
}
```

The TTL means Redis deletes the key automatically. No cleanup job. Set the TTL to your firmware's replay window plus a margin.

The risk: Redis is in-memory. If Redis restarts without AOF or RDB persistence, the dedup state is gone. A delayed duplicate could slip through in the restart window. For warehouse scanning, this is usually acceptable. For a payment system, it is not.

### Pattern 3: DynamoDB Conditional Writes

This is what we use. DynamoDB's conditional write lets you say: "write this item only if the key does not already exist." The check and the write happen atomically.

DynamoDB also supports TTL: a numeric attribute containing a Unix timestamp. After that time, DynamoDB deletes the item automatically. No cleanup job.

This gives you:
- Durability (replicated across three availability zones)
- Automatic cleanup via TTL
- Atomic conditional writes with no race conditions
- Low cost (lock items are tiny and short-lived)

The rest of this post builds this pattern completely.

## Building the Lock Store

Start with an interface. The interface lets you swap in an in-memory implementation for tests.

```go title="lockstore/lockstore.go"
package lockstore

import (
	"context"
	"time"
)

// LockStore is a distributed deduplication store.
// Claim returns true if the caller successfully claimed the ID for the given TTL.
// On a successful claim, call Release when processing is done (or fails).
type LockStore interface {
	Claim(ctx context.Context, id string, ttl time.Duration) (bool, error)
	Release(ctx context.Context, id string) error
}
```

Now the DynamoDB implementation. The key points are in the comments below the code.

```go title="lockstore/dynamo.go"
package lockstore

import (
	"context"
	"errors"
	"fmt"
	"strconv"
	"time"

	"github.com/aws/aws-sdk-go-v2/aws"
	"github.com/aws/aws-sdk-go-v2/service/dynamodb"
	"github.com/aws/aws-sdk-go-v2/service/dynamodb/types"
)

type DynamoLockStore struct {
	client *dynamodb.Client
	table  string
}

func NewDynamoLockStore(client *dynamodb.Client, table string) *DynamoLockStore {
	return &DynamoLockStore{client: client, table: table}
}

func (l *DynamoLockStore) Claim(ctx context.Context, id string, ttl time.Duration) (bool, error) {
	expiry := strconv.FormatInt(time.Now().Add(ttl).Unix(), 10)

	_, err := l.client.PutItem(ctx, &dynamodb.PutItemInput{
		TableName: aws.String(l.table),
		Item: map[string]types.AttributeValue{
			"pk":     &types.AttributeValueMemberS{Value: id},
			"expiry": &types.AttributeValueMemberN{Value: expiry},
		},
		ConditionExpression: aws.String("attribute_not_exists(pk)"),
	})
	if err != nil {
		var ccfe *types.ConditionalCheckFailedException
		if errors.As(err, &ccfe) {
			return false, nil // item already exists: duplicate
		}
		return false, fmt.Errorf("dynamodb put: %w", err)
	}

	return true, nil
}

func (l *DynamoLockStore) Release(ctx context.Context, id string) error {
	_, err := l.client.DeleteItem(ctx, &dynamodb.DeleteItemInput{
		TableName: aws.String(l.table),
		Key: map[string]types.AttributeValue{
			"pk": &types.AttributeValueMemberS{Value: id},
		},
	})
	if err != nil {
		return fmt.Errorf("dynamodb delete: %w", err)
	}
	return nil
}
```

Three things to understand here:

**The condition expression.** `attribute_not_exists(pk)` makes the write atomic. DynamoDB checks the condition and performs the write in a single operation on the server. Two concurrent calls with the same ID cannot both succeed. One gets `ConditionalCheckFailedException`.

**The error check.** `errors.As(err, &ccfe)` is the correct way to detect this error with AWS SDK v2. Do not use `strings.Contains(err.Error(), "ConditionalCheckFailed")`. The SDK's typed errors are stable; error message strings are not.

**The expiry attribute.** DynamoDB's TTL feature requires the attribute to be a Number (not a string). That is why we use `AttributeValueMemberN`. The value is a Unix timestamp in seconds. DynamoDB deletes the item sometime after that timestamp (typically within minutes, guaranteed within 48 hours).

## The Scan Service: First Draft

Let us build the service and work through the design decisions.

```go title="service/scan_service.go"
package service

import (
	"context"
	"fmt"
	"time"

	"github.com/yourorg/rdt-consumer/events"
	"github.com/yourorg/rdt-consumer/lockstore"
	"github.com/yourorg/rdt-consumer/repository"
)

type ScanService struct {
	locks lockstore.LockStore
	repo  repository.ScanRepository
}

func NewScanService(locks lockstore.LockStore, repo repository.ScanRepository) *ScanService {
	return &ScanService{locks: locks, repo: repo}
}

func (s *ScanService) ProcessEvent(ctx context.Context, event events.ScanEvent) error {
	claimed, err := s.locks.Claim(ctx, event.CorrelationID, 30*time.Second)
	if err != nil {
		return fmt.Errorf("claim lock for %s: %w", event.CorrelationID, err)
	}
	if !claimed {
		return nil // duplicate, skip
	}
	defer s.locks.Release(ctx, event.CorrelationID) // nolint:errcheck

	return s.repo.SaveScan(ctx, event)
}
```

This looks correct but has a subtle problem. Read through the logic:

1. Consumer receives event E with correlation ID "abc-123"
2. `Claim` succeeds: the lock is written to DynamoDB with a 30-second TTL
3. `SaveScan` writes the event to the scans table
4. `defer Release` deletes the lock from DynamoDB
5. 10 minutes later, a delayed duplicate of E arrives
6. `Claim` runs: the lock is gone (released in step 4)
7. The duplicate is processed as if it were new

The 30-second TTL made sense as a "hold" during processing. But once we release the lock immediately after, the protection window is zero. A late-arriving duplicate goes right through.

## The Scan Service: Right Design

The lock is not just a mutex for the duration of processing. It is the dedup record that tells future duplicates "this event was already handled."

The TTL should equal your firmware's replay window, not your processing time.

```go title="service/scan_service.go"
package service

import (
	"context"
	"fmt"
	"time"

	"github.com/yourorg/rdt-consumer/events"
	"github.com/yourorg/rdt-consumer/lockstore"
	"github.com/yourorg/rdt-consumer/repository"
)

// deduplicationTTL must be longer than the terminal firmware's maximum replay window.
// Our firmware buffers for up to 12 hours; 25 hours provides margin.
const deduplicationTTL = 25 * time.Hour

type ScanService struct {
	locks lockstore.LockStore
	repo  repository.ScanRepository
}

func NewScanService(locks lockstore.LockStore, repo repository.ScanRepository) *ScanService {
	return &ScanService{locks: locks, repo: repo}
}

func (s *ScanService) ProcessEvent(ctx context.Context, event events.ScanEvent) error {
	claimed, err := s.locks.Claim(ctx, event.CorrelationID, deduplicationTTL)
	if err != nil {
		return fmt.Errorf("claim lock for %s: %w", event.CorrelationID, err)
	}
	if !claimed {
		return nil // duplicate, skip
	}

	if err := s.repo.SaveScan(ctx, event); err != nil {
		// Processing failed. Release the lock so the event can be retried.
		_ = s.locks.Release(ctx, event.CorrelationID)
		return fmt.Errorf("save scan: %w", err)
	}

	return nil // lock stays in DynamoDB for deduplicationTTL
}
```

Now the lock lives for 25 hours. A duplicate arriving 10 minutes later will find the lock and be skipped.

On a processing failure, we release the lock so the next delivery attempt can retry. There is a small window: if `Release` itself fails after a processing error, the lock is stuck until TTL expires (up to 25 hours). Processing errors are rare in our system, so this is an acceptable tradeoff. If processing errors were common, we would use a shorter TTL or a different retry strategy.

## The Repository

The repository writes scan events to a DynamoDB table using a pattern that handles out-of-order delivery.

```go title="repository/scan_repository.go"
package repository

import (
	"context"
	"fmt"
	"time"

	"github.com/aws/aws-sdk-go-v2/aws"
	"github.com/aws/aws-sdk-go-v2/service/dynamodb"
	"github.com/aws/aws-sdk-go-v2/service/dynamodb/types"
	"github.com/yourorg/rdt-consumer/events"
)

// ScanRepository stores and retrieves container scan events.
type ScanRepository interface {
	SaveScan(ctx context.Context, event events.ScanEvent) error
	GetScans(ctx context.Context, containerID string) ([]events.ScanEvent, error)
}

type DynamoScanRepository struct {
	client *dynamodb.Client
	table  string
}

func NewDynamoScanRepository(client *dynamodb.Client, table string) *DynamoScanRepository {
	return &DynamoScanRepository{client: client, table: table}
}

func (r *DynamoScanRepository) SaveScan(ctx context.Context, event events.ScanEvent) error {
	pk := "CONTAINER#" + event.ContainerID
	sk := "SCAN#" + event.ScanTime.UTC().Format(time.RFC3339Nano)

	_, err := r.client.PutItem(ctx, &dynamodb.PutItemInput{
		TableName: aws.String(r.table),
		Item: map[string]types.AttributeValue{
			"pk":             &types.AttributeValueMemberS{Value: pk},
			"sk":             &types.AttributeValueMemberS{Value: sk},
			"correlation_id": &types.AttributeValueMemberS{Value: event.CorrelationID},
			"terminal_id":    &types.AttributeValueMemberS{Value: event.TerminalID},
			"location_code":  &types.AttributeValueMemberS{Value: event.LocationCode},
		},
	})
	if err != nil {
		return fmt.Errorf("save scan %s: %w", event.CorrelationID, err)
	}
	return nil
}
```

The sort key `sk` is the scan time formatted as RFC3339Nano. RFC3339 timestamps sort correctly in lexicographic order because the most significant time component (year) comes first. A DynamoDB query on `pk = CONTAINER#MRKU1234567` returns all scans for that container sorted chronologically, without any extra sort logic.

## Handling Out-of-Order Events

Kafka partitions messages by key. We partition by `terminal_id`. This guarantees that all events from a given terminal arrive in order within a partition.

But events from different terminals interleave. Terminal A might scan container X at 10:00, and terminal B might scan container X at 09:55, but terminal B's event arrives after terminal A's because it was in a different partition. The consumer sees 10:00 before 09:55.

For building a container movement timeline, arrival order is wrong. You want scan time order.

The fix: do not build the timeline on write. Write each event with its `scan_time` as the sort key. Build the timeline on read by querying sorted by `sk`. This is called "sort on read, not on write."

```
Write:
  pk = "CONTAINER#MRKU1234567"
  sk = "SCAN#2026-08-10T09:55:00.000Z"  (09:55 event, arrives second)

  pk = "CONTAINER#MRKU1234567"
  sk = "SCAN#2026-08-10T10:00:00.000Z"  (10:00 event, arrives first)

Read (DynamoDB Query, ascending by sk):
  1. SCAN#2026-08-10T09:55:00.000Z  <- correct chronological order
  2. SCAN#2026-08-10T10:00:00.000Z
```

DynamoDB sorts items by sort key automatically. The query returns the 09:55 scan first regardless of which event arrived first.

## The Kafka Consumer Loop

A complete consumer using `kafka-go`:

```go title="consumer/consumer.go"
package consumer

import (
	"context"
	"encoding/json"
	"fmt"
	"log/slog"

	"github.com/segmentio/kafka-go"
	"github.com/yourorg/rdt-consumer/events"
	"github.com/yourorg/rdt-consumer/service"
)

type Consumer struct {
	reader  *kafka.Reader
	scanner *service.ScanService
	logger  *slog.Logger
}

func New(reader *kafka.Reader, scanner *service.ScanService, logger *slog.Logger) *Consumer {
	return &Consumer{reader: reader, scanner: scanner, logger: logger}
}

// Run processes messages until ctx is cancelled.
func (c *Consumer) Run(ctx context.Context) error {
	for {
		msg, err := c.reader.FetchMessage(ctx)
		if err != nil {
			if ctx.Err() != nil {
				return nil // clean shutdown
			}
			return fmt.Errorf("fetch message: %w", err)
		}

		if err := c.handle(ctx, msg); err != nil {
			c.logger.Error("failed to handle message",
				"offset", msg.Offset,
				"partition", msg.Partition,
				"error", err,
			)
			// Do not commit. Kafka will redeliver. ScanService is idempotent,
			// so redelivery is safe.
			continue
		}

		if err := c.reader.CommitMessages(ctx, msg); err != nil {
			c.logger.Error("failed to commit offset", "error", err)
		}
	}
}

func (c *Consumer) handle(ctx context.Context, msg kafka.Message) error {
	var event events.ScanEvent
	if err := json.Unmarshal(msg.Value, &event); err != nil {
		// Bad JSON cannot be fixed by retrying. Log and commit.
		c.logger.Warn("skipping malformed message",
			"offset", msg.Offset,
			"error", err,
		)
		return nil
	}

	return c.scanner.ProcessEvent(ctx, event)
}
```

Two decisions here worth explaining.

**FetchMessage vs ReadMessage.** `kafka-go`'s `ReadMessage` auto-commits the offset after each fetch. That gives you at-most-once semantics: if your process crashes during processing, the message is lost. We use `FetchMessage` + `CommitMessages` so we control when the offset is committed. We only commit after successful processing.

**Malformed JSON returns nil, not an error.** If we returned an error for bad JSON, the consumer would never commit the offset for that message. Kafka would redeliver it forever. Retrying a message with bad JSON achieves nothing. Log it and move on. Only return errors for failures that might succeed on retry (DynamoDB timeout, network blip).

## In-Memory Implementations for Testing

The `LockStore` and `ScanRepository` interfaces exist so you can test without DynamoDB.

```go title="lockstore/mem.go"
package lockstore

import (
	"context"
	"sync"
	"time"
)

// MemLockStore is a thread-safe in-memory LockStore for tests.
type MemLockStore struct {
	mu    sync.Mutex
	locks map[string]time.Time // id -> expiry time
}

func NewMemLockStore() *MemLockStore {
	return &MemLockStore{locks: make(map[string]time.Time)}
}

func (m *MemLockStore) Claim(ctx context.Context, id string, ttl time.Duration) (bool, error) {
	m.mu.Lock()
	defer m.mu.Unlock()

	if exp, exists := m.locks[id]; exists && time.Now().Before(exp) {
		return false, nil // already claimed and not expired
	}

	m.locks[id] = time.Now().Add(ttl)
	return true, nil
}

func (m *MemLockStore) Release(ctx context.Context, id string) error {
	m.mu.Lock()
	defer m.mu.Unlock()
	delete(m.locks, id)
	return nil
}
```

```go title="repository/mem.go"
package repository

import (
	"context"
	"sync"

	"github.com/yourorg/rdt-consumer/events"
)

// MemScanRepository is a thread-safe in-memory ScanRepository for tests.
type MemScanRepository struct {
	mu    sync.Mutex
	scans map[string][]events.ScanEvent // containerID -> scans
}

func NewMemScanRepository() *MemScanRepository {
	return &MemScanRepository{scans: make(map[string][]events.ScanEvent)}
}

func (m *MemScanRepository) SaveScan(_ context.Context, event events.ScanEvent) error {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.scans[event.ContainerID] = append(m.scans[event.ContainerID], event)
	return nil
}

func (m *MemScanRepository) GetScans(_ context.Context, containerID string) ([]events.ScanEvent, error) {
	m.mu.Lock()
	defer m.mu.Unlock()
	result := make([]events.ScanEvent, len(m.scans[containerID]))
	copy(result, m.scans[containerID])
	return result, nil
}
```

## Testing Idempotency

```go title="service/scan_service_test.go"
package service_test

import (
	"context"
	"fmt"
	"testing"
	"time"

	"github.com/stretchr/testify/assert"
	"github.com/stretchr/testify/require"

func newTestService() (*service.ScanService, *repository.MemScanRepository) {
	locks := lockstore.NewMemLockStore()
	repo := repository.NewMemScanRepository()
	return service.NewScanService(locks, repo), repo
}

func baseEvent() events.ScanEvent {
	return events.ScanEvent{
		CorrelationID: "corr-test-001",
		ContainerID:   "MRKU1234567",
		ScanTime:      time.Now(),
		TerminalID:    "T42",
		LocationCode:  "BEANR-W1",
	}
}

func TestProcessEvent_FirstCall_Saves(t *testing.T) {
	svc, repo := newTestService()
	event := baseEvent()

	err := svc.ProcessEvent(context.Background(), event)
	require.NoError(t, err)

	scans, err := repo.GetScans(context.Background(), event.ContainerID)
	require.NoError(t, err)
	assert.Len(t, scans, 1)
}

func TestProcessEvent_Duplicate_IsIgnored(t *testing.T) {
	svc, repo := newTestService()
	event := baseEvent()

	// First delivery
	require.NoError(t, svc.ProcessEvent(context.Background(), event))

	// Same event arrives again (terminal replay)
	require.NoError(t, svc.ProcessEvent(context.Background(), event))

	scans, err := repo.GetScans(context.Background(), event.ContainerID)
	require.NoError(t, err)
	assert.Len(t, scans, 1, "duplicate should be ignored, not saved twice")
}

func TestProcessEvent_ManyDuplicates(t *testing.T) {
	svc, repo := newTestService()
	event := baseEvent()

	// Terminal had a bad network day and replayed 10 times
	for i := 0; i < 10; i++ {
		err := svc.ProcessEvent(context.Background(), event)
		require.NoError(t, err, "call %d should not error", i+1)
	}

	scans, err := repo.GetScans(context.Background(), event.ContainerID)
	require.NoError(t, err)
	assert.Len(t, scans, 1, "10 duplicate deliveries should produce exactly 1 saved scan")
}

func TestProcessEvent_DistinctEvents_BothSaved(t *testing.T) {
	svc, repo := newTestService()
	ctx := context.Background()

	first := baseEvent()
	first.CorrelationID = "corr-A"

	second := baseEvent()
	second.CorrelationID = "corr-B"
	second.ScanTime = first.ScanTime.Add(5 * time.Minute)

	require.NoError(t, svc.ProcessEvent(ctx, first))
	require.NoError(t, svc.ProcessEvent(ctx, second))

	scans, err := repo.GetScans(ctx, first.ContainerID)
	require.NoError(t, err)
	assert.Len(t, scans, 2, "two distinct scans should both be saved")
}

func TestProcessEvent_DuplicateAfterError_IsRetried(t *testing.T) {
	locks := lockstore.NewMemLockStore()
	repo := repository.NewMemScanRepository()

	// First attempt: inject a repo that always fails
	failRepo := &failOnFirstSave{delegate: repo, shouldFail: true}
	svc := service.NewScanService(locks, failRepo)

	event := baseEvent()

	// First delivery fails
	err := svc.ProcessEvent(context.Background(), event)
	assert.Error(t, err, "expected error from failing repo")

	// Second delivery (Kafka redelivers) should succeed
	failRepo.shouldFail = false
	err = svc.ProcessEvent(context.Background(), event)
	require.NoError(t, err)

	scans, err := repo.GetScans(context.Background(), event.ContainerID)
	require.NoError(t, err)
	assert.Len(t, scans, 1, "retry after error should process the event exactly once")
}

// failOnFirstSave is a ScanRepository that fails on the first SaveScan call.
type failOnFirstSave struct {
	delegate   repository.ScanRepository
	shouldFail bool
}

func (f *failOnFirstSave) SaveScan(ctx context.Context, event events.ScanEvent) error {
	if f.shouldFail {
		return fmt.Errorf("injected failure")
	}
	return f.delegate.SaveScan(ctx, event)
}

func (f *failOnFirstSave) GetScans(ctx context.Context, containerID string) ([]events.ScanEvent, error) {
	return f.delegate.GetScans(ctx, containerID)
}
```

Run the tests with:

The most important test is `TestProcessEvent_DuplicateAfterError_IsRetried`. It checks the whole retry-after-failure cycle: first delivery fails, lock is released, second delivery succeeds, exactly one scan is saved. This is the hardest property to get right.

## Adding Prometheus Metrics

Metrics let you see what is actually happening in production. Without them, you are flying blind.

```go title="service/metrics.go"
package service

import "github.com/prometheus/client_golang/prometheus"

var (
	eventsTotal = prometheus.NewCounterVec(
		prometheus.CounterOpts{
			Name: "rdt_events_total",
			Help: "Scan events processed, by outcome.",
		},
		[]string{"outcome"}, // "processed", "duplicate", "error"
	)

	processingSeconds = prometheus.NewHistogram(
		prometheus.HistogramOpts{
			Name:    "rdt_processing_duration_seconds",
			Help:    "Processing time per scan event.",
			Buckets: []float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0},
		},
	)
)

func init() {
	prometheus.MustRegister(eventsTotal, processingSeconds)
}
```

Add the metric calls to `ProcessEvent`:

```go title="service/scan_service.go"
func (s *ScanService) ProcessEvent(ctx context.Context, event events.ScanEvent) error {
	start := time.Now()

	claimed, err := s.locks.Claim(ctx, event.CorrelationID, deduplicationTTL)
	if err != nil {
		eventsTotal.WithLabelValues("error").Inc()
		return fmt.Errorf("claim lock for %s: %w", event.CorrelationID, err)
	}
	if !claimed {
		eventsTotal.WithLabelValues("duplicate").Inc()
		processingSeconds.Observe(time.Since(start).Seconds())
		return nil
	}

	if err := s.repo.SaveScan(ctx, event); err != nil {
		_ = s.locks.Release(ctx, event.CorrelationID)
		eventsTotal.WithLabelValues("error").Inc()
		processingSeconds.Observe(time.Since(start).Seconds())
		return fmt.Errorf("save scan: %w", err)
	}

	eventsTotal.WithLabelValues("processed").Inc()
	processingSeconds.Observe(time.Since(start).Seconds())
	return nil
}
```

The ratio `duplicate / (processed + duplicate)` is your dedup rate. In normal operation ours sits around 0.3%. A spike to 5% or higher means either a terminal firmware issue or a major network partition at a hub that caused a large batch replay.

Alert rules worth setting up:

```yaml title="alerts.yaml"
- alert: RDTHighDuplicateRate
  expr: |
    rate(rdt_events_total{outcome="duplicate"}[5m])
    /
    rate(rdt_events_total{outcome=~"processed|duplicate"}[5m])
    > 0.05
  for: 5m
  annotations:
    summary: "Duplicate rate above 5% for 5 minutes"

- alert: RDTProcessingErrors
  expr: rate(rdt_events_total{outcome="error"}[1m]) > 0.001
  for: 1m
  annotations:
    summary: "Processing errors above 0.1%"

- alert: RDTSlowProcessing
  expr: histogram_quantile(0.99, rate(rdt_processing_duration_seconds_bucket[5m])) > 0.5
  for: 5m
  annotations:
    summary: "p99 processing latency above 500ms"
```

## DynamoDB Table Setup

You need two tables.

**Locks table** (for deduplication):

```
Table name:      rdt-dedup-locks
Partition key:   pk (String)
TTL attribute:   expiry
Capacity mode:   On-demand
```

**Scans table** (for container movement history):

```
Table name:      rdt-scans
Partition key:   pk (String)  e.g. "CONTAINER#MRKU1234567"
Sort key:        sk (String)  e.g. "SCAN#2026-08-10T14:32:00.000000000Z"
Capacity mode:   On-demand
```

Enable TTL on the locks table: in the DynamoDB console, go to the table, select "Additional settings," then "Manage TTL" and enter `expiry` as the attribute name. No code change needed. DynamoDB reads the `expiry` Number attribute and schedules deletion automatically.

On-demand capacity mode works well for event processing. RDT traffic is spiky: terminals in each timezone all start their shifts at the same local time, creating a wave of events that rolls around the globe through the day. On-demand means you do not need to predict or provision for peaks.

## Common Mistakes

**Releasing the lock immediately after processing.**

If you `defer Release` right after a successful `Claim`, the lock disappears after a few milliseconds. Any duplicate that arrives after that point gets processed. Keep the lock for the full replay window.

**TTL shorter than the firmware's retry window.**

If your terminal replays events for up to 12 hours and your TTL is 30 seconds, late duplicates will not be caught. Know your firmware. Set the TTL to the replay window plus a safety margin.

**Not releasing the lock on error.**

If you claim the lock and then `SaveScan` fails, you must release the lock. Without that release, the event will not be retried for the full TTL duration (25 hours in our case). Always release on error.

**Using `ReadMessage` instead of `FetchMessage` in kafka-go.**

`ReadMessage` auto-commits. You get at-most-once semantics. Crashes during processing lose messages. Use `FetchMessage` + `CommitMessages` and commit only after success.

**Returning errors for malformed events.**

If `json.Unmarshal` fails and you return an error, the consumer never commits the offset. Kafka redelivers forever. Retrying bad JSON is pointless. Log it and commit.

**Trusting correlation IDs from untested firmware.**

UUID v4 is collision-proof in theory, but firmware bugs can cause the same UUID to be generated for different scans. If you are unsure, use `(terminal_id, scan_time)` as the dedup key. A terminal physically cannot scan two different barcodes in the same nanosecond.

## When to Use Which Pattern

| | Unique DB Constraint | Redis SETNX | DynamoDB Conditional Write |
|---|---|---|---|
| **Setup** | Table + index | Redis cluster | DynamoDB table |
| **Cleanup** | Manual job or partitioning | Automatic via TTL | Automatic via TTL |
| **Durability** | High | Low (memory) | High |
| **Throughput** | Moderate | Very high | High |
| **Best when** | Already on PostgreSQL | Sub-ms dedup, can lose state on restart | AWS stack, need durability + auto-expiry |

For most teams on AWS, the DynamoDB pattern is the right default. It is durable, the TTL means no cleanup jobs, and the conditional write is atomic. For teams that already have Redis and can tolerate the restart risk, SETNX is simpler to operate. For teams already on PostgreSQL with moderate traffic, the unique constraint is the least infrastructure to add.

## Summary

Idempotency means: the same input always produces the same output, regardless of how many times you apply it.

Kafka gives you at-least-once delivery by default. Your consumer will see duplicates on crash and rebalance. Making your consumer idempotent means: detect the duplicate, skip it, return success.

The mechanism for detection is a correlation ID: a stable identifier the producer attaches to every event. Two events with the same correlation ID are the same event.

The mechanism for skipping is a dedup store: a database you write to before processing. If the write succeeds (first time you've seen this ID), you process. If it fails because the ID already exists, you skip.

DynamoDB conditional writes give you an atomic dedup store with automatic cleanup. Keep the lock for the full replay window of your producers. Release the lock only on processing failure, so the event can be retried.

Design behind an interface so tests can use an in-memory store. Write tests that verify the duplicate, the retry-after-error, and the distinct-events cases. Add Prometheus metrics so you can see the duplicate rate and react when it spikes.

The result is a consumer that correctly handles the messiness of real hardware on real networks, at whatever scale you need.
