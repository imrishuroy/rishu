## Before You Start

Three concepts this post builds on.

### 1. Kubernetes Basics

Kubernetes runs containerized workloads. Three things to know:

```
+---------------------+
|   Deployment        |  Declares: "run 3 replicas of image:v2"
|  +---------------+  |
|  |     Pod       |  |  One running instance of your container.
|  | [container]   |  |  Pods are ephemeral; they restart with new IPs.
|  +---------------+  |
+---------------------+
         |
+---------------------+
|   Service           |  Stable DNS name and IP that load-balances
|   user-service:80   |  to all healthy pods with matching labels.
+---------------------+
```

A `Deployment` describes desired state. Kubernetes keeps actual state matching it. If a pod crashes, Kubernetes starts a new one. The `Service` gives callers a stable address regardless of which pod handles the request.

### 2. Container Images

A container image is a snapshot of a filesystem: your compiled Go binary plus the OS libraries it needs. When you run `go build`, you get a binary. When you wrap it in a Docker image, you get a portable unit that runs the same way everywhere.

```dockerfile
FROM golang:1.23 AS builder
WORKDIR /app
COPY . .
RUN go build -o user-service .

FROM gcr.io/distroless/static-debian12
COPY --from=builder /app/user-service /user-service
ENTRYPOINT ["/user-service"]
```

Each microservice ships as one image. Independent deployment means you can build and push a new image for one service without touching any other.

### 3. What a Distributed Trace Is

When a request enters your system at the gateway and fans out to three backend services, a distributed trace records the whole journey as a tree of spans.

```
trace_id = abc123
  span: gateway.handle          0ms -- 220ms
    span: orders.createOrder   10ms -- 200ms
      span: payments.charge    20ms --  95ms
      span: inventory.reserve 100ms -- 150ms
```

Each span records which service ran it, how long it took, and what the parent span was. Together they answer: "where did this request spend its time?" The observability section covers how to produce and read these in Go.

## Event-Driven Architecture, CQRS, and Event Sourcing

### Q32. What is event-driven architecture?

Services communicate by publishing events ("something happened") instead of calling each other directly. Any service that cares subscribes and reacts.

```
[Order Service]  publishes "order.created"
                     |
         +-----------+-----------+
         v           v           v
   [Email Svc]  [Analytics]  [Inventory]
   sends conf.  records sale  decrements
   email                      stock
```

The Order Service does not know who consumes the event. Adding the Inventory service did not require changing the Order Service. This is the key benefit: producers and consumers are decoupled.

Here is a minimal in-process event bus to illustrate the pattern:

```go title="eventbus.go"
package eventbus

import "sync"

// Handler is a function that processes an event payload.
type Handler func(payload []byte)

// Bus is a simple in-process publish/subscribe event bus.
type Bus struct {
    mu       sync.RWMutex
    handlers map[string][]Handler
}

func New() *Bus {
    return &Bus{handlers: make(map[string][]Handler)}
}

// Subscribe registers a handler for an event type.
func (b *Bus) Subscribe(eventType string, h Handler) {
    b.mu.Lock()
    defer b.mu.Unlock()
    b.handlers[eventType] = append(b.handlers[eventType], h)
}

// Publish delivers a payload to all handlers registered for eventType.
func (b *Bus) Publish(eventType string, payload []byte) {
    b.mu.RLock()
    defer b.mu.RUnlock()
    for _, h := range b.handlers[eventType] {
        h(payload)
    }
}
```

In production, replace the in-process bus with Kafka or RabbitMQ. The service code stays the same; only the `Publish` and `Subscribe` implementations change.

### Q33. What is the difference between an event and a command?

An **event** describes something that already happened: past tense, immutable, broadcast to whoever cares. `OrderPlaced`, `PaymentCharged`, `UserRegistered`.

A **command** is an instruction to do something: imperative, directed at a specific recipient with an expected outcome. `PlaceOrder`, `ChargePayment`, `RegisterUser`.

```go title="event_vs_command.go"
package domain

// OrderPlacedEvent is an event: it happened, it is a fact.
// Published to all interested parties.
type OrderPlacedEvent struct {
    OrderID    string
    CustomerID string
    TotalCents int
    OccurredAt string
}

// PlaceOrderCommand is a command: directed at the order service,
// expects a result (order ID or error).
type PlaceOrderCommand struct {
    CustomerID string
    Items      []CommandItem
}

type CommandItem struct {
    SKU      string
    Quantity int
}
```

Naming convention is the simplest enforcement: events use past tense nouns, commands use imperative verb phrases.

### Q34. What is CQRS?

Command Query Responsibility Segregation separates the write model from the read model. The write side handles commands: validate, apply business rules, persist. The read side handles queries: return data optimized for the UI, often denormalized.

```
Write side:                       Read side:
[PlaceOrder command]              [GetOrderSummary query]
      |                                   |
[OrderHandler]                    [OrderSummaryView]
validates + persists                  reads from
to orders table                  order_summaries table
      |
  emits event
      |
      v
[Projector goroutine]
reads event, updates
order_summaries table
```

```go title="cqrs.go"
package orders

import (
    "context"
    "database/sql"
    "fmt"
    "time"
)

// Write side: handles the PlaceOrder command.
type PlaceOrderCommand struct {
    CustomerID string
    Items      []CommandItem
    TotalCents int
}

type CommandItem struct {
    SKU      string
    Quantity int
}

func HandlePlaceOrder(ctx context.Context, db *sql.DB, cmd PlaceOrderCommand) (string, error) {
    orderID := fmt.Sprintf("ord-%d", time.Now().UnixNano())

    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return "", fmt.Errorf("begin: %w", err)
    }
    defer tx.Rollback()

    if _, err = tx.ExecContext(ctx,
        `INSERT INTO orders (id, customer_id, total_cents, status, created_at)
         VALUES ($1, $2, $3, 'pending', NOW())`,
        orderID, cmd.CustomerID, cmd.TotalCents,
    ); err != nil {
        return "", fmt.Errorf("insert order: %w", err)
    }

    return orderID, tx.Commit()
}

// Read side: handles the GetOrderSummary query from a denormalized view.
type OrderSummary struct {
    ID           string `json:"id"`
    CustomerName string `json:"customer_name"`
    TotalCents   int    `json:"total_cents"`
    Status       string `json:"status"`
    ItemCount    int    `json:"item_count"`
}

func QueryOrderSummary(ctx context.Context, db *sql.DB, orderID string) (OrderSummary, error) {
    var s OrderSummary
    err := db.QueryRowContext(ctx,
        `SELECT id, customer_name, total_cents, status, item_count
         FROM order_summaries WHERE id = $1`,
        orderID,
    ).Scan(&s.ID, &s.CustomerName, &s.TotalCents, &s.Status, &s.ItemCount)
    if err != nil {
        return OrderSummary{}, fmt.Errorf("query order summary %s: %w", orderID, err)
    }
    return s, nil
}
```

Use CQRS when read and write workloads are fundamentally different: heavy analytical reads that would slow writes, different authorization rules for reads and writes, or a need to serve multiple denormalized views from one write model.

### Q35. What is event sourcing?

Instead of storing the current state of an entity, store the sequence of events that produced that state. Current state is derived by replaying the events.

```
Order #42 event log:
  1. OrderPlaced    {customer_id: "c1", items: [...]}
  2. ItemRemoved    {sku: "KB-001"}
  3. CouponApplied  {code: "SAVE10", discount_cents: 500}
  4. OrderShipped   {tracking: "ABC123"}

Current state = fold of all 4 events.
```

```go title="event_sourcing.go"
package orders

import "fmt"

type OrderEvent interface {
    Apply(o *OrderState)
}

type OrderState struct {
    ID         string
    Status     string
    TotalCents int
    Items      []string
}

type OrderPlaced struct {
    OrderID    string
    TotalCents int
}

func (e OrderPlaced) Apply(o *OrderState) {
    o.ID = e.OrderID
    o.TotalCents = e.TotalCents
    o.Status = "placed"
}

type CouponApplied struct {
    DiscountCents int
}

func (e CouponApplied) Apply(o *OrderState) {
    o.TotalCents -= e.DiscountCents
}

type OrderShipped struct {
    Tracking string
}

func (e OrderShipped) Apply(o *OrderState) {
    o.Status = fmt.Sprintf("shipped:%s", e.Tracking)
}

// Replay derives the current state by folding all events.
func Replay(events []OrderEvent) OrderState {
    var state OrderState
    for _, e := range events {
        e.Apply(&state)
    }
    return state
}
```

Pros: complete audit log, time travel (replay to any point in time), easy to add new read models by replaying the log.

Cons: schema evolution is hard (old events must still be replayable after the schema changes), queries require materialized views (you cannot query the event log directly for most use cases).

Use event sourcing when you genuinely need an audit log or time travel. Do not use it because it sounds clever.

### Q36. Can you use CQRS without event sourcing?

Yes. CQRS just means separate read and write models. You can store state in a normal SQL table on the write side and maintain a separate read-optimized view using a background projector or database triggers. Event sourcing is an optional addition that gives you the event log. Most teams should start with CQRS only and add event sourcing if the audit or time-travel use case becomes real.

## Observability: Logs, Metrics, and Traces

### Q47. What are the three pillars of observability?

| Pillar | Question it answers | Tool examples |
|--------|--------------------|-|
| Logs | What happened at this point in time? | Loki, Elasticsearch |
| Metrics | How is the system behaving over time? | Prometheus, Datadog |
| Traces | What was the path of this specific request? | Jaeger, Tempo, Zipkin |

You need all three. Logs give granular detail. Metrics give aggregate trends and power alerts. Traces connect a single request across all services.

### Q48. What is distributed tracing?

Every request gets a unique trace ID. Every step within a service gets a span. Spans reference a parent span, building a tree.

```
trace_id = abc123
  span: gateway.handle        [0ms ---------> 220ms]
    span: orders.createOrder    [10ms ------> 200ms]
      span: payments.charge       [20ms -> 95ms]
      span: inventory.reserve     [100ms --> 150ms]
```

The trace shows that `payments.charge` and `inventory.reserve` ran in parallel (they overlap in time) and that `orders.createOrder` waited for both before returning.

```go title="tracing.go"
package main

import (
    "context"
    "fmt"

    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/attribute"
    "go.opentelemetry.io/otel/codes"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracehttp"
    "go.opentelemetry.io/otel/sdk/resource"
    sdktrace "go.opentelemetry.io/otel/sdk/trace"
    semconv "go.opentelemetry.io/otel/semconv/v1.21.0"
)

// InitTracer sets up an OTLP trace exporter sending to Jaeger or any
// OpenTelemetry collector.
func InitTracer(ctx context.Context, serviceName string) (*sdktrace.TracerProvider, error) {
    exporter, err := otlptracehttp.New(ctx)
    if err != nil {
        return nil, fmt.Errorf("create exporter: %w", err)
    }

    tp := sdktrace.NewTracerProvider(
        sdktrace.WithBatcher(exporter),
        sdktrace.WithResource(resource.NewWithAttributes(
            semconv.SchemaURL,
            semconv.ServiceNameKey.String(serviceName),
        )),
    )
    otel.SetTracerProvider(tp)
    return tp, nil
}

var tracer = otel.Tracer("orders")

func createOrder(ctx context.Context, customerID string) (string, error) {
    ctx, span := tracer.Start(ctx, "orders.createOrder")
    defer span.End()

    span.SetAttributes(attribute.String("customer.id", customerID))

    orderID, err := persistOrder(ctx, customerID)
    if err != nil {
        span.RecordError(err)
        span.SetStatus(codes.Error, err.Error())
        return "", err
    }

    span.SetAttributes(attribute.String("order.id", orderID))
    return orderID, nil
}

func persistOrder(ctx context.Context, customerID string) (string, error) {
    // DB write here.
    return "ord-123", nil
}
```

### Q49. Why does context propagation matter?

A trace spans multiple services. For spans in different services to link to the same trace, the trace context must travel with the request. The standard header is `traceparent` (W3C Trace Context specification).

```go title="propagation.go"
package main

import (
    "context"
    "net/http"

    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/propagation"
)

// OutgoingRequest injects the current trace context into the HTTP request headers.
func OutgoingRequest(ctx context.Context, req *http.Request) {
    otel.GetTextMapPropagator().Inject(ctx, propagation.HeaderCarrier(req.Header))
    // This adds: traceparent: 00-{traceID}-{spanID}-01
}

// IncomingRequest extracts the trace context from incoming request headers.
func IncomingRequest(r *http.Request) context.Context {
    return otel.GetTextMapPropagator().Extract(r.Context(), propagation.HeaderCarrier(r.Header))
}
```

If you use the OpenTelemetry HTTP middleware, this happens automatically. For custom transports (gRPC metadata, Kafka headers, message queues), you must propagate explicitly.

### Q50. What metrics should every service expose?

The RED method covers service-level health:

- **Rate**: requests per second
- **Errors**: error rate (proportion of requests returning 5xx)
- **Duration**: latency at p50, p95, p99

The USE method covers resource health:

- **Utilization**: how busy is the CPU, memory, or connection pool
- **Saturation**: queue depth, wait time
- **Errors**: hardware or OS errors

```go title="metrics.go"
package main

import (
    "net/http"
    "strconv"
    "time"

    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
    requestsTotal = prometheus.NewCounterVec(
        prometheus.CounterOpts{
            Name: "http_requests_total",
            Help: "Total HTTP requests by method, path, and status.",
        },
        []string{"method", "path", "status"},
    )

    requestDuration = prometheus.NewHistogramVec(
        prometheus.HistogramOpts{
            Name:    "http_request_duration_seconds",
            Help:    "HTTP request latency.",
            Buckets: []float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5},
        },
        []string{"method", "path"},
    )
)

func init() {
    prometheus.MustRegister(requestsTotal, requestDuration)
}

type statusWriter struct {
    http.ResponseWriter
    status int
}

func (sw *statusWriter) WriteHeader(code int) {
    sw.status = code
    sw.ResponseWriter.WriteHeader(code)
}

// MetricsMiddleware records RED metrics for every request.
func MetricsMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        sw := &statusWriter{ResponseWriter: w, status: http.StatusOK}

        next.ServeHTTP(sw, r)

        duration := time.Since(start).Seconds()
        status := strconv.Itoa(sw.status)
        requestsTotal.WithLabelValues(r.Method, r.URL.Path, status).Inc()
        requestDuration.WithLabelValues(r.Method, r.URL.Path).Observe(duration)
    })
}

func main() {
    mux := http.NewServeMux()
    mux.Handle("/metrics", promhttp.Handler())
    mux.Handle("/orders/", MetricsMiddleware(http.HandlerFunc(handleOrder)))
    http.ListenAndServe(":8080", mux)
}

func handleOrder(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
}
```

### Q51. What is structured logging?

Structured logging writes log entries as JSON with consistent fields instead of free-form strings. Fields are searchable and aggregatable in log management systems.

```go title="structured_logging.go"
package main

import (
    "context"
    "log/slog"
    "os"

    "go.opentelemetry.io/otel/trace"
)

func newLogger() *slog.Logger {
    return slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
        Level: slog.LevelInfo,
    }))
}

func logOrderCreated(ctx context.Context, logger *slog.Logger, orderID, customerID string) {
    // Extract trace ID from context so logs and traces can be correlated.
    spanCtx := trace.SpanFromContext(ctx).SpanContext()
    traceID := spanCtx.TraceID().String()

    logger.InfoContext(ctx, "order created",
        "order_id", orderID,
        "customer_id", customerID,
        "trace_id", traceID,
        "service", "orders",
    )
}
```

Output:

```json
{
  "time": "2026-11-18T10:00:00Z",
  "level": "INFO",
  "msg": "order created",
  "order_id": "ord-123",
  "customer_id": "cust-42",
  "trace_id": "abc123def456...",
  "service": "orders"
}
```

The `trace_id` field lets you jump from a log entry directly to the trace in Jaeger or Tempo.

## Testing Microservices

### Q52. What is the testing pyramid for microservices?

```
             /\
            /  \         End-to-end: few, expensive, slow, flaky
           /    \        Deploy all services, test real user flows.
          /------\
         /        \      Contract / integration: more
        /          \     Verify service boundaries hold.
       /------------\
      /              \   Component / service-level: many
     /                \  Test one service with real DB, fake dependencies.
    /------------------\
   /                    \ Unit: most
  /____________________  \ Fast, isolated, test single functions.
```

Do not try to end-to-end test everything. E2E tests are expensive to maintain, slow to run, and flaky. Push coverage down into unit and contract tests.

### Q53. What are consumer-driven contract tests?

The consumer of an API defines the contract it expects (the fields it uses, the status codes it handles). The provider runs that contract as part of its CI pipeline. If the provider breaks the contract, the test fails before the change is deployed.

```go title="contract_test.go"
package contract_test

import (
    "encoding/json"
    "net/http"
    "net/http/httptest"
    "testing"
)

// UserServiceContract defines what the order service expects from the user service.
// This test lives in the order service repo.
type userResponse struct {
    ID   string `json:"id"`
    Name string `json:"name"`
}

// TestUserServiceContract verifies the user service returns at minimum the
// fields the order service depends on.
func TestUserServiceContract(t *testing.T) {
    // In a real Pact setup, the provider runs this generated interaction.
    // Here we show the shape of the assertion.
    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.URL.Path != "/users/usr-1" {
            http.NotFound(w, r)
            return
        }
        w.Header().Set("Content-Type", "application/json")
        json.NewEncoder(w).Encode(userResponse{ID: "usr-1", Name: "Rishu Kumar"})
    }))
    defer srv.Close()

    resp, err := http.Get(srv.URL + "/users/usr-1")
    if err != nil {
        t.Fatalf("request failed: %v", err)
    }
    defer resp.Body.Close()

    if resp.StatusCode != http.StatusOK {
        t.Fatalf("expected 200, got %d", resp.StatusCode)
    }

    var user userResponse
    if err := json.NewDecoder(resp.Body).Decode(&user); err != nil {
        t.Fatalf("decode failed: %v", err)
    }
    if user.ID == "" {
        t.Error("expected non-empty id")
    }
    if user.Name == "" {
        t.Error("expected non-empty name")
    }
}
```

The Pact framework automates this: consumers generate a pact file from their tests; providers replay the pact. If a provider changes a response shape in a way that breaks any consumer's pact, the CI fails.

### Q54. How do you test message-driven services?

Use a fake broker backed by channels for unit and integration tests:

```go title="fake_broker_test.go"
package consumer_test

import (
    "encoding/json"
    "testing"
)

type FakeBroker struct {
    messages map[string][][]byte
}

func NewFakeBroker() *FakeBroker {
    return &FakeBroker{messages: make(map[string][][]byte)}
}

func (f *FakeBroker) Publish(topic string, payload []byte) error {
    f.messages[topic] = append(f.messages[topic], payload)
    return nil
}

func (f *FakeBroker) MessagesFor(topic string) [][]byte {
    return f.messages[topic]
}

type OrderCreatedEvent struct {
    OrderID    string `json:"order_id"`
    CustomerID string `json:"customer_id"`
}

func TestOrderCreatedPublished(t *testing.T) {
    broker := NewFakeBroker()

    event := OrderCreatedEvent{OrderID: "ord-1", CustomerID: "cust-42"}
    payload, _ := json.Marshal(event)
    broker.Publish("order.created", payload)

    msgs := broker.MessagesFor("order.created")
    if len(msgs) != 1 {
        t.Fatalf("expected 1 message, got %d", len(msgs))
    }

    var got OrderCreatedEvent
    if err := json.Unmarshal(msgs[0], &got); err != nil {
        t.Fatalf("unmarshal: %v", err)
    }
    if got.OrderID != "ord-1" {
        t.Errorf("expected ord-1, got %s", got.OrderID)
    }
}
```

For integration tests, spin up a real Kafka or RabbitMQ instance using `testcontainers-go`. Test both the happy path and failure paths: broker unavailable, malformed payload, duplicate delivery.

### Q55. How do you test for resilience?

**Toxiproxy** is a TCP proxy that lets you inject latency, bandwidth limits, and connection drops:

```go title="toxiproxy_test.go"
package resilience_test

import (
    "fmt"
    "net"
    "net/http"
    "net/http/httptest"
    "testing"
    "time"
)

// LatencyProxy wraps a real server and injects latency.
// In production tests, replace with Toxiproxy for more sophisticated control.
func LatencyProxy(t *testing.T, backend *httptest.Server, latency time.Duration) string {
    t.Helper()
    ln, err := net.Listen("tcp", "127.0.0.1:0")
    if err != nil {
        t.Fatal(err)
    }

    go func() {
        for {
            conn, err := ln.Accept()
            if err != nil {
                return
            }
            go func(c net.Conn) {
                defer c.Close()
                time.Sleep(latency)
                // In a real proxy, forward bytes to backend.
                // Simplified here for illustration.
            }(conn)
        }
    }()

    t.Cleanup(func() { ln.Close() })
    return fmt.Sprintf("http://%s", ln.Addr())
}

func TestCircuitBreakerOpensUnderLatency(t *testing.T) {
    // Arrange: a backend that is very slow.
    slowBackend := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        time.Sleep(5 * time.Second)
        w.WriteHeader(http.StatusOK)
    }))
    defer slowBackend.Close()

    client := &http.Client{Timeout: 100 * time.Millisecond}

    // Act: send 5 requests that all time out.
    var failures int
    for i := 0; i < 5; i++ {
        _, err := client.Get(slowBackend.URL)
        if err != nil {
            failures++
        }
    }

    // Assert: all 5 timed out.
    if failures != 5 {
        t.Errorf("expected 5 timeouts, got %d", failures)
    }
}
```

Beyond unit tests: **chaos testing** (Chaos Mesh for Kubernetes, Gremlin) kills real pods and injects real network failures. **Game days** are scheduled exercises where the team simulates an incident and practices response. Run load tests past peak expected traffic before you need to handle it for real.

## API Versioning and Evolution

### Q56. What are the main strategies for versioning APIs?

| Strategy | Example | Pros | Cons |
|----------|---------|------|------|
| URL path | `/v1/users`, `/v2/users` | Explicit, easy to route, easy to debug | Duplication in URL |
| Header | `Accept: application/vnd.app.v2+json` | Clean URLs | Less visible, harder to test with curl |
| Schema additive | Add fields, never remove | No new URL needed | Consumers must tolerate unknown fields |

URL versioning is the most common because it is explicit and every tool (curl, browser, logging) works without special configuration.

```go title="versioning.go"
package main

import (
    "encoding/json"
    "net/http"
)

type UserV1 struct {
    ID   string `json:"id"`
    Name string `json:"name"`
}

type UserV2 struct {
    ID          string `json:"id"`
    Name        string `json:"name"`
    DisplayName string `json:"display_name"` // new in v2
    AvatarURL   string `json:"avatar_url"`   // new in v2
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("/v1/users/", handleUsersV1)
    mux.HandleFunc("/v2/users/", handleUsersV2)
    http.ListenAndServe(":8080", mux)
}

func handleUsersV1(w http.ResponseWriter, r *http.Request) {
    user := UserV1{ID: "usr-1", Name: "Rishu Kumar"}
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(user)
}

func handleUsersV2(w http.ResponseWriter, r *http.Request) {
    user := UserV2{
        ID:          "usr-1",
        Name:        "Rishu Kumar",
        DisplayName: "rishuroy",
        AvatarURL:   "https://avatars.example.com/usr-1.png",
    }
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(user)
}
```

### Q57. What changes are backward-compatible?

**Safe** (additive, consumers that do not use the new field are unaffected):

- Add optional fields to responses
- Add new endpoints
- Add new event types to a topic
- Relax validation (accept more values)

**Breaking** (consumers that depend on existing behavior will fail):

- Remove or rename a field
- Change a field's type (string to integer)
- Tighten validation (reject values you previously accepted)
- Change a URL structure
- Change HTTP status codes that consumers branch on

When you must make a breaking change: deploy v2 alongside v1, migrate consumers to v2, retire v1 after all consumers have migrated. Never remove v1 until every consumer is off it.

### Q58. How do you evolve an event schema?

The same additive rule: add fields, never remove them. Consumers must tolerate unknown fields (do not use strict deserialization that fails on extra fields).

```go title="schema_evolution.go"
package events

// OrderCreatedV1 is the original event schema.
type OrderCreatedV1 struct {
    OrderID    string `json:"order_id"`
    CustomerID string `json:"customer_id"`
    TotalCents int    `json:"total_cents"`
}

// OrderCreatedV2 adds source_channel. Consumers reading V1 events
// will see source_channel as empty string, which is acceptable.
type OrderCreatedV2 struct {
    OrderID       string `json:"order_id"`
    CustomerID    string `json:"customer_id"`
    TotalCents    int    `json:"total_cents"`
    SourceChannel string `json:"source_channel"` // new, optional for consumers
}
```

For breaking changes to events, publish to a new topic in parallel:

```
Old topic: orders.created.v1    (keep running until all consumers migrate)
New topic: orders.created.v2    (new schema)
```

Use a schema registry (Confluent Schema Registry with Avro or Protobuf) set to `BACKWARD` compatibility mode. The registry rejects schema changes that would break existing consumers.

## Deployment and Release Patterns

### Q59. Why is independent deployment the headline benefit of microservices?

Before microservices, every team's deploy is everyone else's deploy. A hotfix in one team must wait for all other teams to sign off on a shared release. After microservices, each team deploys their service on their own schedule. A bug fix in the payment service ships in minutes, not days.

This is the main reason organizations adopt microservices. It is an organizational benefit, not a technical one.

### Q60. What deployment patterns are common?

**Rolling update**: replace instances one at a time. The default in Kubernetes. Zero downtime if health checks are configured correctly.

**Blue-green**: run two identical environments. Switch traffic from blue (current) to green (new) atomically. Easy rollback: switch back to blue.

**Canary**: route a small percentage of traffic to the new version. Ramp up if metrics stay healthy. Safest for risky changes.

**Shadow**: copy real traffic to the new version without affecting users. The new version processes requests but its responses are discarded. Useful for testing correctness before switching.

Here is a canary deployment using Kubernetes labels and two Deployments sharing one Service:

```yaml title="canary-deployment.yaml"
# Stable deployment: 9 replicas
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-stable
spec:
  replicas: 9
  selector:
    matchLabels:
      app: orders
      track: stable
  template:
    metadata:
      labels:
        app: orders
        track: stable
    spec:
      containers:
        - name: orders
          image: orders:v1.9.2
---
# Canary deployment: 1 replica (roughly 10% of traffic)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-canary
spec:
  replicas: 1
  selector:
    matchLabels:
      app: orders
      track: canary
  template:
    metadata:
      labels:
        app: orders
        track: canary
    spec:
      containers:
        - name: orders
          image: orders:v1.10.0-rc1
---
# One Service routes to ALL pods with app=orders, regardless of track.
# 9 stable + 1 canary = ~10% of requests hit the canary.
apiVersion: v1
kind: Service
metadata:
  name: orders
spec:
  selector:
    app: orders
  ports:
    - port: 80
      targetPort: 8080
```

If the canary looks healthy after 15 minutes, scale it to 10 replicas and scale stable to 0.

### Q61. What is a feature flag?

A runtime toggle for a code path. Deploy code dark (behind a flag that is off), enable it for a percentage of users or a specific user segment without redeploying.

```go title="feature_flags.go"
package flags

// Flags is an interface so you can swap in a real provider
// (LaunchDarkly, Unleash, GrowthBook) without changing call sites.
type Flags interface {
    IsEnabled(flag string, userID string) bool
}

// StaticFlags is a simple in-process implementation for testing.
type StaticFlags struct {
    enabled map[string]bool
}

func NewStaticFlags(enabled map[string]bool) *StaticFlags {
    return &StaticFlags{enabled: enabled}
}

func (f *StaticFlags) IsEnabled(flag string, _ string) bool {
    return f.enabled[flag]
}
```

```go title="checkout_handler.go"
package main

import (
    "net/http"
    "example.com/flags"
)

func checkoutHandler(ff flags.Flags) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        userID := r.Header.Get("X-User-ID")

        if ff.IsEnabled("new-checkout-flow", userID) {
            newCheckout(w, r)
            return
        }
        oldCheckout(w, r)
    }
}

func newCheckout(w http.ResponseWriter, r *http.Request) { w.Write([]byte("new")) }
func oldCheckout(w http.ResponseWriter, r *http.Request) { w.Write([]byte("old")) }
```

Feature flags decouple deploy from release. You can ship code to production days before enabling it, and roll back by toggling a flag rather than reverting a deploy.

### Q62. Should every service really pick its own database?

In theory yes. In practice, the operational cost is real. Running ten different database technologies means ten different backup strategies, ten different monitoring setups, and ten sets of expertise to maintain.

Most teams standardize on one or two databases (Postgres plus Redis is a common pair) and only branch out for genuine technical need: Elasticsearch for full-text search, Cassandra for time-series at massive scale. "Best tool for the job" is true; "every team picks a different tool" leads to operational chaos and knowledge silos.

## Service Mesh

### Q63. What is a service mesh?

A service mesh adds a sidecar proxy (Envoy) alongside every service instance. All inbound and outbound traffic passes through the proxy. The proxy handles:

- mTLS (mutual TLS: both sides authenticate each other)
- Automatic retries and timeouts
- Circuit breaking
- Traffic shifting (canary releases at the network layer)
- Distributed tracing (adds `traceparent` headers automatically)
- Metrics (request rate, error rate, latency per service pair)

```
[Order Service]  <-->  [Envoy sidecar A]
                               |
                           mTLS tunnel
                               |
[Payment Service] <--> [Envoy sidecar B]
```

The application code connects to `localhost`. The sidecar intercepts the connection and handles the network concerns. The application does not need to know the mesh exists.

Examples: Istio (Envoy-based, feature-rich), Linkerd (Rust-based, lighter), Consul Connect.

### Q64. When should you adopt a service mesh?

Adopt a service mesh when:

- You have many services in many languages and want uniform mTLS and observability without changing each service's code.
- Security requirements mandate mutual TLS between all service-to-service calls.
- You want traffic splitting (canary releases) at the network layer without application changes.
- You are comfortable operating Envoy and the mesh control plane.

Do not adopt a mesh because a conference talk made it sound interesting. A service mesh adds:

- A control plane that must be kept highly available.
- Envoy proxies that consume CPU and memory per pod.
- Another layer to debug when networking breaks.
- Significant expertise to operate correctly.

Start without a mesh. Add one when you have a specific problem it solves.

### Q65. How is a service mesh different from an API gateway?

| | API gateway | Service mesh |
|---|---|---|
| Traffic type | North-south (clients to services) | East-west (service to service) |
| Main concerns | Auth, rate limiting, public API surface | mTLS, retries, observability |
| Deployment | One gateway per environment | Sidecar proxy per pod |
| Configuration | Centralized routing rules | Distributed per-proxy config |

A production system typically uses both. The API gateway handles everything at the edge. The service mesh handles everything inside the cluster.

## Anti-Patterns and When Not to Use Microservices

### Q66. What are the most common microservices anti-patterns?

**Distributed monolith**: services that must deploy together because they share a database or call each other synchronously in tight cycles. Covered in Part 1.

**Chatty services**: a single user request triggers dozens of synchronous service calls in a chain. The latency of each call adds up. The probability of one of them failing multiplies. Redesign by: pushing data to where it is needed with events, using async communication, or merging services that always talk to each other.

**Shared database**: two services reading from or writing to the same tables. Eliminates the ability to deploy independently and couples schema evolution.

**Nano-services**: one service per function (e.g., `compute-discount-service`). The overhead of network calls, deployments, and on-call rotations is not justified for a single function. Merge it into the domain service that owns the concept.

**Inconsistent error handling**: every service returns errors in a different format. Callers must handle them differently. Agree on a standard error envelope early and enforce it.

**Mock-heavy testing**: test suites that mock every service dependency. Tests pass but the real wiring fails in production. Use contract tests and integration tests with real dependencies.

**No observability**: you find out about outages from customers instead of from alerts. Add structured logging, metrics, and distributed tracing before you need them.

### Q67. What are the fallacies of distributed computing?

Eight assumptions that every newcomer makes and that all turn out false in practice. Knowing them helps you anticipate failures before they bite you.

1. **The network is reliable.** Packets drop. Links fail. Switches reboot.
2. **Latency is zero.** Network calls add milliseconds. At scale, milliseconds matter.
3. **Bandwidth is infinite.** Serializing large payloads is slow. Schemas matter.
4. **The network is secure.** Traffic can be intercepted. Use mTLS inside the cluster.
5. **Topology doesn't change.** Services scale up and down. IP addresses change. Use service discovery.
6. **There is one administrator.** Different teams own different services. Coordinate change management.
7. **Transport cost is zero.** Serialization, deserialization, and routing cost CPU time.
8. **The network is homogeneous.** Different cloud regions, different cloud providers, different on-premise setups all behave differently.

Every microservices outage traces back to assuming one of these. Use them as a checklist when designing a new interaction between services.

### Q68. What is the two-pizza team rule?

Amazon's heuristic: a team should be small enough to feed with two pizzas, roughly 6 to 10 people. Small teams communicate efficiently, make decisions quickly, and can own a service end to end. When a team grows beyond this, ownership diffuses and coordination overhead rises.

This is why microservices align naturally with organizational structure: one bounded context per service, one team per service.

### Q69. Why do distributed transactions keep coming up as a hard problem?

Because cross-service consistency is fundamentally unsolved in a way that is both correct and practical. Every attempt to make it look easy, through 2PC, generic saga frameworks, or "distributed transaction" libraries, hides failure modes that surface under load or during partial failures.

The honest answer is sagas with compensations and idempotency keys. They require you to design every operation to be retryable and every compensation to be safe to call more than once. That is real work. It does not disappear behind an abstraction.

### Q70. When are microservices the wrong choice?

Microservices are the wrong choice when:

- **New product, small team, requirements still moving**: you are optimizing for delivery speed, not deploy independence. A monolith lets you refactor freely across the whole codebase.
- **Single team, single deploy cadence**: if one team deploys everything together anyway, you get none of the organizational benefits of microservices.
- **Latency-critical paths**: each service call adds network latency. A trading system or real-time game server cannot afford extra round trips.
- **Tightly coupled domain**: if every business operation touches the same data and enforces cross-cutting invariants, decomposing it into services means constantly fighting the boundary.
- **Limited ops capacity**: if the team cannot operate Kubernetes, a container registry, and a distributed tracing stack, the operational overhead will slow you down more than the architecture helps.

### Q71. What is the right starting point for a new product?

A **modular monolith**: one deployable unit with clean module boundaries inside it. Each module has its own package, its own types, and communicates with other modules through well-defined interfaces. No circular imports between modules.

```
cmd/
  api/
    main.go          one binary

internal/
  users/             users module: owns users table
    service.go
    repository.go
  orders/            orders module: owns orders table
    service.go
    repository.go
  payments/          payments module: owns payments table
    service.go
    repository.go
```

When a module clearly grows beyond the rest (different scaling needs, different team, different release cadence), extract it into a service. By the time you have extracted five services, you know your domain well enough to draw the remaining boundaries correctly.

### Q72. What are the sensible defaults for a microservices system?

One bounded context per service. One database per service, no sharing.

Async events for cross-service communication. Synchronous calls only when you need an answer right now.

Outbox pattern for reliable event publishing. Idempotent consumers to handle at-least-once delivery.

Timeouts on every external call. Retries with exponential backoff and jitter. Circuit breakers on every downstream dependency.

Distributed tracing from day one. Structured logging with trace IDs. RED metrics per service.

Schema additive: add fields, never remove them. Breaking changes go through a versioned API or a parallel event topic.

Independent deploys. Canary releases for risky changes. Feature flags to decouple deploy from release.

## How to Get Better at This

### Build It

**OpenTelemetry in Go**: add OTel to an existing Go service. Export traces to Jaeger running locally:

```bash
docker run -d -p 16686:16686 -p 4318:4318 jaegertracing/all-in-one
```

Set the environment variable `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` and instrument two services that call each other. Open `http://localhost:16686` and find a trace that spans both services.

**CQRS**: implement a task list (create task, complete task) with a separate write model (normalized SQL) and read model (denormalized view with task count per user). Write a projector that updates the read model from events. Verify the read model is eventually consistent after writes.

**Canary in Kubernetes**: deploy a service with two Deployments (stable and canary) sharing one Service using label selectors. Use `kubectl scale` to shift traffic by changing replica counts. Watch the metrics change as more traffic hits the canary.
